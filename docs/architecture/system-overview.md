# WorkNotOver: Обзор архитектуры системы

## Назначение

`WorkNotOver` — это сценарная система для:

- загрузки и нормализации исходных производственных данных;
- расчёта базовой добычи нефти, газа, жидкости и эффекта ГТМ;
- расчёта экономики;
- построения и оптимизации графика КРС;
- проверки инфраструктурных ограничений;
- ручной корректировки графика КРС в planner;
- повторного пересчёта добычи и экономики по вручную изменённому графику;
- ведения сценариев и их сравнения.

Система должна поддерживать как автоматический контур оптимизации, так и ручной контур календарного планирования.

---

## Общая модель системы

В системе есть три связанных контура:

1. Контур данных
2. Расчётно-оптимизационный контур
3. Контур planner и сценарной обратной связи

### 1. Контур данных

- загрузка Excel;
- ручной ввод параметров и конфигураций;
- ручной ввод коэффициентов отказности по `LU` и `SLOY`;
- preview;
- сопоставление колонок;
- нормализация;
- сохранение `Dataset` и `ManualInputSet` в storage layer;
- подготовка structured datasets.

### 2. Расчётно-оптимизационный контур

- расчёт базовой добычи;
- расчёт добычи газа и `GOR`;
- расчёт эффекта ГТМ;
- расчёт экономики;
- построение графика КРС;
- проверка инфраструктурных ограничений;
- выбор лучшего сценария.

### 3. Контур planner и сценарной обратной связи

- передача графика КРС в planner;
- ручная корректировка календаря;
- сохранение planner revision;
- возврат скорректированного графика в расчёт;
- создание нового сценария;
- повторный расчёт добычи и экономики.

Это означает, что planner — отдельный модуль, а не просто экран или bridge.

На уровне пользовательской навигации это должно отражаться так:

- раздел sidebar `Исходные данные`
  - новый сценарный UI-контур подготовки входных данных и конфигураций;
- раздел sidebar `Планировщик КРС`
  - отдельный готовый модуль `Planner`.

Новый раздел `Исходные данные` заменяет старый раздел `Загрузка графика`, но не заменяет `Планировщик КРС`.

## Список модулей

## Module A: Загрузка и нормализация Excel

Зона ответственности:

- загрузка Excel-файлов;
- приём ручных исходных вводных;
- preview;
- auto-mapping и manual mapping колонок;
- валидация;
- нормализация данных;
- нормализация доменной иерархии `LU -> SLOY -> WellPad -> WellState`;
- сохранение `Dataset / DatasetVersion / DatasetReference`;
- сохранение `ManualInputSet / ManualInputReference`;
- подготовка входных наборов данных для остальных модулей.

Выход:

- normalized well dataset;
- normalized GTM dataset;
- normalized infrastructure dataset;
- manual input configs;
- validation report.

---

## Module B: Расчёт базовой добычи и эффекта ГТМ

Зона ответственности:

- расчёт базового профиля нефти и жидкости;
- расчёт базового профиля газа и `GOR`;
- расчёт обводнённости;
- расчёт эффекта ГТМ;
- расчёт инкрементальных и накопленных эффектов по нефти, газу и жидкости;
- формирование `ProductionScenario`.

Выход:

- скважинные профили;
- агрегированный профиль;
- эффекты по мероприятиям;
- результат расчётного сценария.

---

## Module C: Экономика

Зона ответственности:

- расчёт экономики отдельных мероприятий;
- расчёт экономики сценария;
- расчёт KPI сценария.

Выход:

- `GtmEconomicsResult[]`;
- `EconomicsResult`;
- итоговые KPI.

---

## Module D: График КРС и оптимизатор

Зона ответственности:

- построение допустимого графика КРС;
- учёт количества бригад;
- учёт длительностей по типам;
- учёт календарных ограничений;
- генерация сценариев;
- оптимизация очередности мероприятий;
- вызов инфраструктурной проверки;
- выбор лучшего графика.

Выход:

- `KrsScheduleScenario`;
- `OptimizationResult`.

Важно:

Module D не реализует инфраструктурные ограничения внутри себя, а получает ответ о допустимости сценария из Module E.

---

## Module E: Инфраструктурные ограничения

Зона ответственности:

- проверка сценарного профиля добычи на ограничения инфраструктуры;
- учёт дат ввода объектов;
- учёт ограничений линейных и площадочных объектов;
- возврат нарушений в optimizer.

Выход:

- `InfrastructureConstraintCheckResult`;
- перечень нарушений;
- первый момент нарушения;
- сведения по объекту, метрике и величине превышения.

Важно:

Модуль валидирует сценарий, но не исправляет его сам.

---

## Module F: Planner

Planner — самостоятельный модуль системы.

Зона ответственности:

- визуализация графика КРС;
- версионирование графиков;
- drag-and-drop редактирование;
- ручной перенос мероприятий;
- сохранение planner revisions;
- хранение editable schedule representation.

Planner является владельцем ручной календарной модели графика КРС.

Выход:

- `PlannerScheduleRevision`;
- planner-side versions of schedule;
- manual revisions ready for recalculation.

---

## Module G: Сценарный UI и обратный пересчёт

Зона ответственности:

- orchestration UI для расчёта, экономики, оптимизации и сценариев;
- лист `Загрузка`;
- лист `Характеристики пласта`;
- лист `Экономические вводные`;
- лист `Ограничения бригад`;
- лист `Схема работы оптимизатора`;
- запуск расчёта;
- запуск оптимизации;
- отправка графика в planner;
- импорт ревизии из planner;
- запуск пересчёта по planner revision;
- сравнение сценариев.

Иными словами:

- `Module F` владеет ручным графиком;
- `Module G` владеет пользовательским сценарием работы с системой и новым пересчётом на основе planner edits.

Дополнительное правило для UI:

- внешний готовый график КРС загружается через лист `Загрузка`,
- нормализуется в `Module A`,
- затем открывается в `Module F: Planner`,
- где создаётся новая версия графика с типом `загруженный`.

Дополнительное правило для входных конфигураций:

- коэффициент отказности задаётся вручную в разделе `Исходные данные`;
- область действия коэффициента — `LU` или `SLOY`;
- канонически он хранится как часть manual input layer и затем используется `Module D`.

## Ключевой сценарный цикл

```text
Excel / параметры
  -> Module A
  -> Module B
  -> Module C
  -> Module D
  -> Module E
  -> Module D (учёт infra-response)
  -> Module F (planner)

Planner manual edit
  -> Module F
  -> Module G
  -> Module B
  -> Module C
  -> new Scenario
```

## Расшифровка зависимостей

- `A -> B`
  Module B получает нормализованные скважины и ГТМ.

- `A -> D`
  Module D получает нормализованные мероприятия и правила планирования.

- `A -> E`
  Module E получает инфраструктурные объекты и связи.

- `B -> C`
  Экономика считается поверх рассчитанного профиля добычи.

- `B -> D`
  Optimizer использует профиль добычи и эффекты ГТМ.

- `B -> E`
  Инфраструктурный модуль использует рассчитанный профиль добычи.

- `B -> G`
  Scenario UI показывает результаты расчёта добычи.

- `C -> D`
  Optimizer использует экономические оценки в score / target function.

- `C -> G`
  Scenario UI отображает экономику сценариев.

- `D <-> E`
  Optimizer отправляет сценарий на infra-check и получает ответ о нарушениях.

- `D -> F`
  Оптимизированный или просто построенный график КРС передаётся в planner.

- `D -> G`
  Scenario UI показывает результаты оптимизации и рейтинг сценариев.

- `F -> G`
  Planner передаёт ревизии графика в сценарный UI/контур пересчёта.

- `G -> B`
  После ручной правки planner UI инициирует повторный расчёт добычи.

- `G -> C`
  После ручной правки planner UI инициирует повторный расчёт экономики.

---

## Почему Planner выделен в отдельный модуль

Planner — это не просто визуальный экран. Он:

- хранит версии графика;
- позволяет редактировать график;
- создаёт planner revisions;
- участвует в сценарном цикле как источник новой календарной версии.

Если не выделять его в отдельный модуль, смешиваются:

- planner UI;
- ручная календарная модель;
- bridge;
- сценарный пересчёт.

Выделение Planner в отдельный модуль делает архитектуру чище.

## Границы ответственности между Planner и Scenario UI

### Module F: Planner

Владеет:

- editable schedule;
- planner revision;
- drag-and-drop календарной логикой;
- planner versions.

### Module G: Scenario UI and feedback loop

Владеет:

- запуском сценариев;
- сравнением сценариев;
- пересчётом после planner revision;
- сценарием пользователя от загрузки до recalculation.

## Архитектурные правила

1. Модули общаются только через согласованные контракты.
2. Shared schemas являются каноническим интерфейсом между модулями.
3. UI не дублирует бизнес-расчёты backend.
4. Planner revision всегда создаёт новый сценарий, а не перезаписывает старый.
5. Infrastructure validation отделена от optimizer.
6. Любое изменение контракта должно сопровождаться обновлением docs.
7. Planner является отдельным bounded context, а не приложением “внутри” optimizer.

## Рекомендуемый порядок разработки

1. Core contracts и scenario model
2. Module A
3. Module B
4. Module C
5. Module E
6. Module D
7. Module F
8. Module G

Причины:

- сначала нормализованные данные;
- затем расчётный контур;
- затем инфраструктурная валидация;
- затем optimizer;
- затем отдельный planner;
- затем полный сценарный UI и feedback loop.

---

## Критерии успешной архитектуры

Архитектура считается успешной, когда:

- импорт данных воспроизводим и нормализован;
- расчёт добычи и экономики повторяем;
- график КРС может автоматически строиться и оптимизироваться;
- инфраструктурные ограничения проверяются как отдельный валидатор;
- planner хранит ручные ревизии графика как самостоятельный модуль;
- ручные правки из planner возвращаются в расчёт как новые сценарии;
- сценарии можно сравнивать и трассировать по происхождению.
