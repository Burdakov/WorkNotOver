# WorkNotOver: Обзор архитектуры системы

## Назначение

`WorkNotOver` — это сценарная система для:

- загрузки и нормализации исходных производственных данных из Excel/CSV/YAML;
- расчёта добычи нефти, воды, газа, жидкости, обводнённости, `GOR` и пластового давления;
- расчёта экономики;
- построения и оптимизации графика КРС;
- проверки инфраструктурных ограничений;
- ручной корректировки графика КРС в planner;
- повторного пересчёта добычи и экономики по вручную изменённому графику;
- ведения сценариев и их сравнения.

Система должна поддерживать как автоматический контур оптимизации, так и ручной контур календарного планирования.

---

## Общая модель системы

В системе есть три связанных контура:

1. Контур данных
2. Расчётно-оптимизационный контур
3. Контур planner и сценарной обратной связи

### 1. Контур данных

- загрузка Excel/CSV/YAML/текстовые с любым расшрением;
- ручной ввод параметров и конфигураций;
- загрузка отдельного dataset `NIZ` по скважинам;
- загрузка истории добычи;
- загрузка истории закачки;
- загрузка PVT/SCAL/ROCK/region properties;
- загрузка forecast scenario definitions;
- ручной ввод коэффициентов отказности по `LU` и `SLOY`;
- preview;
- сопоставление колонок;
- нормализация;
- сохранение `Dataset` и `ManualInputSet` в storage layer;
- подготовка structured datasets.

### 2. Расчётно-оптимизационный контур

- подготовка полного комплекса исходных данных для гидродинамического моделирования
- history matching по обводнённости, пластовому давлению, дебитам жидкости и нефти;
- расчёт насыщенности, обводнённости, газа и `GOR`;
- расчёт forecast scenarios;
- расчёт экономики;
- построение графика КРС;
- проверка инфраструктурных ограничений;
- выбор лучшего сценария.

### 3. Контур planner и сценарной обратной связи

- передача графика КРС в planner;
- ручная корректировка календаря;
- сохранение planner revision;
- возврат скорректированного графика в расчёт;
- создание нового сценария;
- повторный расчёт добычи и экономики.

Это означает, что planner — отдельный модуль, а не просто экран или bridge.

На уровне пользовательской навигации это должно отражаться так:

- раздел sidebar `Сценарии`
  - основной сценарный UI-контур, внутри которого живут загрузка, нормализация, привязка datasets и manual inputs;
- все сценарные разделы системы используют один active scenario context, включающий имя сценария и его канонические input bindings;
- раздел sidebar `Планировщик КРС`
  - отдельный готовый модуль `Planner`.

Раздел `Сценарии` заменяет старый раздел `Загрузка графика`, но не заменяет `Планировщик КРС`.

## Список модулей

## Module A: Загрузка и нормализация исходных файлов

Зона ответственности:

- загрузка Excel/CSV/YAML-файлов/текстовых файлов любого расширения;
- приём ручных исходных вводных;
- preview;
- auto-mapping и manual mapping колонок;
- валидация;
- нормализация данных;
- нормализация доменной иерархии `LU -> SLOY -> WellPad -> WellState`;
- сохранение `Dataset / DatasetVersion / DatasetReference`;
- сохранение `ManualInputSet / ManualInputReference`;
- подготовка входных наборов данных для остальных модулей.

Выход:
- набор файлов для гидродинамического симулятора OPM flow и его обвязки в части контроля и генерации schedule секции


---

## Module B: OPM Flow hydrodynamic forecast и расчёт добычи

Зона ответственности:

- подготовка OPM/Eclipse-compatible case из нормализованных данных `Module A`;
- генерация `RUNSPEC`, `GRID`, `PROPS`, `REGIONS`, `SOLUTION`, `SCHEDULE`, `SUMMARY`;
- запуск внешнего симулятора `OPM Flow` через `flow` executable;
- сохранение raw OPM artifacts как неизменяемого scenario/run evidence;
- импорт `.EGRID`, `.INIT`, `.SMSPEC`, `.UNSMRY`, `.UNRST`, `.RFT`, `.PRT/.LOG` в нормализованные scenario-bound результаты;
- формирование well/field/group time series, grid static state, grid dynamic state, material balance by region/FIPNUM и diagnostics;
- расчёт forecast scenarios с injection schedules, producer constraints, shut-ins, conversions, link changes и pressure constraints через schedule/deck;
- формирование регионов для скважин используя pywaterflood
- автоматическое формирование связанного сценария `чистая База` без GTM для сценарного сравнения и отображения слоя `БАЗА`;
- расчёт инкрементальных и накопленных эффектов по нефти, газу и жидкости;
- формирование `SimulationRun` и `ProductionScenario` на основании импортированных результатов OPM.

Выход:

- скважинные профили;
- агрегированный профиль;
- `SimulationRun`;
- `SimulationArtifact[]`;
- `OpmCaseManifest`;
- `OpmImportResult`;
- `WaterfloodAnalysisPayload` / `ReservoirSimulationAnalysisPayload` для UI-диагностики ячеек, связей, насыщенности, давления и факт-расчёт аналитики;
- material balance by cell/region/FIPNUM;
- history/forecast diagnostics;
- эффекты по мероприятиям;
- результат расчётного сценария.

Внешние open source инструменты:

- production path `Module B` требует доступного `OPM Flow` runtime для реального гидродинамического расчёта;
- backend должен уметь валидировать и готовить case без запуска `flow`, чтобы base tests не требовали внешнего симулятора;
- `res2df` / `opm.io` используются как optional importer layer для OPM/Eclipse results;
- pywaterflood не являtтся расчетным ядром, а используется для генерации регионов для скважин как один из кубов симулятора.

---

## Module C: Экономика

Зона ответственности:

- расчёт экономики отдельных мероприятий;
- расчёт экономики сценария;
- расчёт KPI сценария.

Выход:

- `GtmEconomicsResult[]`;
- `EconomicsResult`;
- итоговые KPI.

---

## Module D: График КРС и оптимизатор

Зона ответственности:

- построение допустимого графика КРС;
- учёт количества бригад;
- учёт длительностей по типам;
- учёт календарных ограничений;
- генерация сценариев;
- оптимизация очередности мероприятий;
- вызов инфраструктурной проверки;
- выбор лучшего графика.

Выход:

- `KrsScheduleScenario`;
- `OptimizationResult`.

Важно:

Module D не реализует инфраструктурные ограничения внутри себя, а получает ответ о допустимости сценария из Module E.

---

## Module E: Инфраструктурные ограничения

Зона ответственности:

- проверка сценарного профиля добычи на ограничения инфраструктуры;
- учёт дат ввода объектов;
- учёт ограничений линейных и площадочных объектов;
- возврат нарушений в optimizer.
- формиурет групповой контроль для секции schedule при расчёте прогнозных сценариев в OPM Flow

Выход:

- `InfrastructureConstraintCheckResult`;
- перечень нарушений;
- первый момент нарушения;
- сведения по объекту, метрике и величине превышения.

Важно:

Модуль валидирует сценарий, но не исправляет его сам.

---

## Module F: Planner

Planner — самостоятельный модуль системы.

Зона ответственности:

- визуализация графика КРС;
- версионирование графиков;
- drag-and-drop редактирование;
- ручной перенос мероприятий;
- сохранение planner revisions;
- хранение editable schedule representation.

Planner является владельцем ручной календарной модели графика КРС.

Выход:

- `PlannerScheduleRevision`;
- planner-side versions of schedule;
- manual revisions ready for recalculation.

---

## Module G: Сценарный UI и обратный пересчёт

Зона ответственности:

- orchestration UI для расчёта, экономики, оптимизации и сценариев;
- лист `Загрузка`;
- лист `Характеристики пласта`;
- лист `Экономические вводные`;
- лист `Ограничения бригад`;
- лист `Схема работы оптимизатора`;
- запуск расчёта;
- запуск оптимизации;
- отправка графика в planner;
- импорт ревизии из planner;
- запуск пересчёта по planner revision;
- сравнение сценариев.

Дополнительный принцип:

- `Module G` строится по модели `Scenario-first`;
- пользовательский workflow начинается с выбора существующего сценария или создания нового;
- выбор источника графика КРС, datasets и manual inputs выполняется как часть сценарного workflow, а не как независимые действия без сценарного контекста;
- список сценариев является главным входом в пользовательский сценарный контур.
- для сценариев с GTM пользовательский контур должен иметь доступ к связанному производному сценарию `чистая База`, который автоматически формируется расчетным контуром и используется в разделе `Добыча` как источник слоя `БАЗА`.

Иными словами:

- `Module F` владеет ручным графиком;
- `Module G` владеет пользовательским сценарием работы с системой и новым пересчётом на основе planner edits.

Дополнительное правило для UI:

- внешний готовый график КРС загружается через лист `Загрузка`,
- нормализуется в `Module A`,
- затем открывается в `Module F: Planner`,
- где создаётся новая версия графика с типом `загруженный`.

Дополнительное правило сценарного workflow:

- если в `Planner` выполнено действие `Создать версию`, `Module F` создаёт новый `PlannerScheduleRevision`;
- затем `Module G` автоматически формирует новую версию сценария на основе активного сценарного контекста и полученного revision;
- новая версия сценария автоматически появляется в списке сценариев без отдельного ручного шага создания.
- после этого именно новая planner-derived версия становится текущим active scenario для `Сценарии`, `Добыча` и дальнейших переходов в `Planner`.

Дополнительное правило для входных конфигураций:

- коэффициент отказности задаётся вручную в разделе `Сценарии`;
- область действия коэффициента — `LU` или `SLOY`;
- канонически он хранится как часть manual input layer и затем используется `Module D`.

## Ключевой сценарный цикл

```text
Excel / CSV / YAML / параметры
  -> Module A
  -> Module B
  -> Module C
  -> Module D
  -> Module E
  -> Module D (учёт infra-response)
  -> Module F (planner)

Planner manual edit
  -> Module F
  -> Planner action `Создать версию`
  -> Module G
  -> automatic scenario version creation
  -> Module B (читает `PlannerScheduleRevision` из `Module F`)
  -> Module C
  -> new Scenario
```

### Module B: новая drainage-1D ветка

Внутри `A -> B` для настройки модели и прогноза добычи действует дополнительная подготовительная цепочка:

```text
well trajectories
  + perforations
  + production history
  + injection history
  + reserves / pore volumes / properties
  -> ContactInterval
  -> Drainage1DConnection matrix
  -> Drainage1DModelSpec[]
  -> batch OPM Flow runs
  -> history matching / calibration
  -> normalized scenario-bound production outputs
```

Эта ветка остается частью `Module B`.

## Расшифровка зависимостей

- `A -> B`
  Module B получает нормализованные скважины, историю добычи/закачки, ячейки разработки, PVT/SCAL/ROCK properties, forecast config/scenarios.

- `A -> D`
  Module D получает нормализованные мероприятия и правила планирования.

- `A -> E`
  Module E получает инфраструктурные объекты и связи.

- `B -> C`
  Экономика считается поверх рассчитанного профиля добычи.

- `B -> D`
  Optimizer использует профиль добычи и эффекты ГТМ.

- `B -> E`
  Инфраструктурный модуль использует рассчитанный профиль добычи.

- `B -> G`
  Scenario UI показывает результаты расчёта добычи.

- `C -> D`
  Optimizer использует экономические оценки в score / target function.

- `C -> G`
  Scenario UI отображает экономику сценариев.

- `D <-> E`
  Optimizer отправляет сценарий на infra-check и получает ответ о нарушениях.

- `D -> F`
  Оптимизированный или просто построенный график КРС передаётся в planner.

- `F -> B`
  При planner-side recalculation `Module B` читает `PlannerScheduleRevision` напрямую из `Planner`; `Module G` при этом остаётся orchestration-контуром запуска.

- `D -> G`
  Scenario UI показывает результаты оптимизации и рейтинг сценариев.

- `F -> G`
  Planner передаёт ревизии графика и событие `Создать версию` в сценарный UI/контур пересчёта.

- `G -> B`
  Scenario UI инициирует повторный расчёт добычи, но source of truth для `PlannerScheduleRevision` остаётся `Module F`.

- `G -> C`
  После ручной правки planner UI инициирует повторный расчёт экономики и связанного сценарного контура.

## Почему Planner выделен в отдельный модуль

Planner — это не просто визуальный экран. Он:

- хранит версии графика;
- позволяет редактировать график;
- создаёт planner revisions;
- участвует в сценарном цикле как источник новой календарной версии.

Если не выделять его в отдельный модуль, смешиваются:

- planner UI;
- ручная календарная модель;
- bridge;
- сценарный пересчёт.

Выделение Planner в отдельный модуль делает архитектуру чище.

## Границы ответственности между Planner и Scenario UI

### Module F: Planner

Владеет:

- editable schedule;
- planner revision;
- drag-and-drop календарной логикой;
- planner versions.

### Module G: Scenario UI and feedback loop

Владеет:

- запуском сценариев;
- списком сценариев;
- сравнением сценариев;
- пересчётом после planner revision;
- сценарием пользователя от загрузки до recalculation.

## Архитектурные правила

1. Модули общаются только через согласованные контракты.
2. Shared schemas являются каноническим интерфейсом между модулями.
3. UI не дублирует бизнес-расчёты backend.
4. Planner revision всегда создаёт новый сценарий, а не перезаписывает старый.
5. Infrastructure validation отделена от optimizer.
6. Любое изменение контракта должно сопровождаться обновлением docs.
7. Planner является отдельным bounded context, а не приложением “внутри” optimizer.

## Рекомендуемый порядок разработки

1. Core contracts и scenario model
2. Module A
3. Module B
4. Module C
5. Module E
6. Module D
7. Module F
8. Module G

Причины:

- сначала нормализованные данные;
- затем расчётный контур;
- затем инфраструктурная валидация;
- затем optimizer;
- затем отдельный planner;
- затем полный сценарный UI и feedback loop.

## Критерии успешной архитектуры

Архитектура считается успешной, когда:

- импорт данных воспроизводим и нормализован;
- расчёт добычи и экономики повторяем;
- график КРС может автоматически строиться и оптимизироваться;
- инфраструктурные ограничения проверяются как отдельный валидатор;
- planner хранит ручные ревизии графика как самостоятельный модуль;
- ручные правки из planner возвращаются в расчёт как новые сценарии;
- сценарии можно сравнивать и трассировать по происхождению.
