# Контракт Module G

## Модуль

`Module G: Сценарный UI и обратный пересчёт`

## Назначение

`Module G` владеет пользовательским сценарным контуром работы с системой и оркестрирует:

- загрузку и выбор исходных данных;
- ввод ручных параметров;
- запуск расчёта;
- запуск оптимизации;
- открытие графика в `Planner`;
- повторный пересчёт после `planner revisions`.

`Module G` не владеет самим editable-графиком `Planner`, но владеет пользовательским сценарием движения по системе от загрузки входных данных до получения нового сценария.
При этом при planner-side recalculation сам `PlannerScheduleRevision` читается `Module B` напрямую из `Module F`, а `Module G` оркестрирует запуск и пользовательский поток пересчёта.

## Принцип Scenario-first

`Module G` строится вокруг сущности `Scenario`, а не вокруг набора независимых листов ввода.

Любой пользовательский workflow в `Module G` начинается с выбора существующего сценария или создания нового.

Каждый сценарий должен иметь собственные ссылки на входные данные и собственные сценарные атрибуты, определённые в `core-data-model`, включая:

- `DatasetReference` для обязательных dataset-входов;
- `ManualInputReference`;
- `source_type`;
- `parent_scenario_id`, если сценарий производный;
- временное окно сценария;
- связанные outputs расчёта и planner-side revisions.

`Module G` не определяет состав сценарных атрибутов заново, а использует канонические сущности из `core-data-model`.

Во всей системе должен существовать один активный выбранный сценарий. Разделы `Сценарии`, `Добыча` и сценарные переходы в `Planner` должны работать с одним и тем же active scenario context, а не хранить независимые локальные выборы.

Имя сценария является частью этого общего контекста: пользователь задаёт `Scenario.name` один раз, после чего это имя должно отображаться и переиспользоваться во всех разделах системы и в производных сценариях planner-side flow.

`Planner` должен использовать этот же active scenario context напрямую. Если выбран planner-derived scenario, `Planner` открывает связанную `PlannerScheduleRevision`; если выбран сценарий ветки `Внешний график`, `Planner` открывает `external_krs_schedule`, привязанный к этому сценарию.

`Planner` не должен открывать произвольный dataset вне сценарного контекста и не должен опираться на несохранённые локальные значения формы. Источник графика для `Planner` всегда определяется уже сохранённым active scenario context.

## Дерево workflow сценария

Интерфейс `Module G` должен визуализировать сценарный workflow как дерево состояний.

Базовый workflow:

1. `Создать новый сценарий`
2. `Выбрать источник графика КРС`
3. `Собрать входные данные сценария`
4. `Проверить полноту сценария`
5. `Запустить расчёт`
6. `Открыть / передать в Planner`
7. `Получить planner revision`
8. `Создать новую версию сценария`

### Узел 1. Создать новый сценарий

Пользователь создаёт новый `Scenario` или выбирает существующий сценарий из списка.

На этом шаге задаются базовые атрибуты сценария:

- `name`
- `source_type`
- `parent_scenario_id`, если сценарий производный
- `forecast_start_date`
- `forecast_end_date`

### Узел 2. Выбрать источник графика КРС

Пользователь выбирает один из двух вариантов:

- `Новый график КРС`
- `Загрузить существующий график КРС`

Если выбран `Новый график КРС`, дальнейшее формирование графика идёт через расчётно-оптимизационный контур.

Если выбран `Загрузить существующий график КРС`, используется dataset типа `external_krs_schedule`, загруженный через `Module A`.

Выбор источника графика КРС не заменяет создание сценария, а является частью атрибутов сценарного workflow.

## Основная UI-структура

В левом sidebar должны существовать три разных раздела верхнего уровня:

- `Сценарии`
- `Добыча`
- `Планировщик КРС`

`Сценарии` — это основной сценарный раздел `Module G`, который заменяет самостоятельный раздел `Исходные данные` и вбирает в себя весь функционал загрузки, нормализации и привязки входных данных к сценарию.

`Добыча` — это отдельный сценарный раздел `Module G`, который отображает сохранённые результаты `Module B`, даёт выбрать сценарий расчёта и анализировать профиль добычи по иерархии `LU -> SLOY -> WellPad -> скважина`. 

`Планировщик КРС` — это отдельный готовый модуль `Module F: Planner`, а не один из листов сценарного UI.

Экран `Сценарии` должен состоять из трёх основных зон:

1. компактная верхняя toolbar сценария в одну строку;
2. центральный workflow-canvas;
3. нижний `Scenario workbench`.

В верхней toolbar постоянно видны:

- `Сценарий`
- `Период`
- `Сохранить контекст`
- `Рассчитать`

`Workflow-canvas` должен строиться как ветвящийся сценарный маршрут.

Стартовый узел canvas:

- `Источник графика`

Из него должны выходить три визуально объединённых source-узла:

- `Внешний график`
- `Сформировать график`
- `Полученный из Planner`

Каждый source-узел должен:

- быть явно выбираемым;
- показывать статус готовности;
- показывать галочку после того, как источник выбран и загружен в сценарный контекст.

Отдельного нижнего блока `Scenario Context`, дублирующего source-ветки canvas, быть не должно.

Основной путь для режимов `Внешний график` и `Полученный из Planner`:

- `Исходные данные`
- `Module B: Forecast`
- `Module C: Economics`

Для этих двух режимов canvas не должен вести пользователя через `Module D: KRS Optimizer`.

Отдельная ветка для режима `Сформировать график`:

- `Исходные данные`
- `Module B: Forecast`
- `Module C: Economics`
- `Module E: Infra Check`
- `Module D: KRS Optimizer`
- `Planner Revision`

На этой ветке `Module D: KRS Optimizer` остаётся центральным расчетным узлом, а связи между `Forecast`, `Economics`, `Infra Check` и `KRS Optimizer` должны быть нарисованы стрелками.

При выборе режима `Сформировать график` верхняя прямая ветка `Исходные данные -> Forecast -> Economics` должна оставаться видимой, но визуально приглушаться как неактивный путь. Активной должна быть только ветка, которая ведёт в `KRS Optimizer`.

На active generated-ветке canvas не должен рисовать отдельные карточки `Infrastructure`, `Module F: Planner` и `Новая версия сценария`. `Infra Check` должен отображаться как один из feed-элементов, сходящихся в `KRS Optimizer`, а downstream-результатом на canvas должна оставаться карточка `Planner Revision`.

Узел `Исходные данные` на canvas показывается как единый grouped-блок, внутри которого доступны clickable-подузлы:

- `Wells`
- `NIZ`
- `ГТМ`
- `Вытеснение`
- `Экономика`
- `KRS ограничения`
- `Infrastructure`

Для каждого такого подузла должен отображаться статус готовности прямо на квадратике:

- зелёная галочка, если входные данные полностью заданы и валидны;
- жёлтый минус, если данные заполнены частично и в конфигурации есть незаполненные обязательные поля;
- отсутствие индикатора, если узел ещё не заполнялся.

Для dataset-узлов `Wells`, `NIZ`, `ГТМ` и `Infrastructure` статус должен определяться не только фактом привязки dataset, но и канонической `ScenarioInputValidation`.

Если сценарий использует ветку `Внешний график`, а во внешнем графике КРС есть скважины, отсутствующие в `wells` dataset или `gtm` dataset, узлы `Wells` и/или `ГТМ` должны переходить в состояние `partial` с жёлтым минусом.
Если у скважин из `wells` dataset или `gtm` dataset нет значений в scenario-bound dataset `niz`, узлы `Wells`, `NIZ` и/или `ГТМ` должны переходить в состояние `partial` с жёлтым минусом.

В таком состоянии сценарий считается недозаполненным, и верхнее действие `Рассчитать` должно быть недоступно до устранения несоответствия.

Раздел `Добыча` не должен отображаться на canvas и не должен быть частью сценарного экрана. Он является отдельным result-view поверх уже сохранённых outputs.

В `Scenario workbench` вводятся листы:

1. `Загрузка`
2. `Характеристики пласта`
3. `Экономические вводные`
4. `Ограничения бригад`
5. `Схема работы оптимизатора`

Эти листы образуют нижнюю рабочую область сценария.

`Scenario workbench` предназначен для:

- загрузки Excel;
- preview исходных данных;
- нормализации заголовков;
- auto-mapping и manual mapping;
- сохранения datasets;
- привязки datasets к активному сценарию;
- редактирования `ManualInputSet` по типам;
- настройки параметров расчётно-оптимизационного контура.

`Scenario workbench` не должен показывать все листы одновременно.

Он должен работать как нижний inspector-диалог:

- пользователь кликает по узлу canvas;
- нижняя панель показывает только данные и редакторы этого узла;
- все остальные листы и редакторы скрываются;
- переключение узла на canvas автоматически меняет содержимое нижней панели.

Дополнительное правило для source-узла `Внешний график`:

- при выборе `Внешний график` нижний inspector должен сразу показывать upload-flow для `external_krs_schedule`;
- upload-flow должен использовать тот же сценарий, что и для `Wells` и `ГТМ`:
  - загрузка Excel;
  - preview;
  - всплывающее окно `Mapping колонок`;
  - автопредложение сопоставления;
  - возможность сразу согласиться с предложенным mapping;
- сохранение dataset и привязка его к активному сценарию.

Дополнительное правило для source-узла `Полученный из Planner`:

- при выборе `Полученный из Planner` нижний inspector должен показывать список опубликованных `PlannerScheduleRevision` для базового сценария;
- пользователь должен иметь возможность выбрать одну конкретную revision;
- для выбранной revision UI должен показывать:
  - `version_name`
  - дату revision
  - количество событий
  - уже созданный derived scenario, если он существует;
- inspector должен содержать явное действие `Применить revision`;
- действие `Применить revision` должно вызывать создание новой версии сценария через сценарный backend-flow, а не требовать ручного создания сценария пользователем.

Примеры:

- клик по `Wells` показывает выбранную версию wells dataset, компактную строку загрузки/выбора файла и сводную таблицу `LU -> куст -> скважина` с количеством скважин и текущими нефтью / жидкостью / газом;
- клик по `NIZ` показывает выбранную версию scenario-bound NIZ dataset, компактную строку загрузки/выбора файла и сводную таблицу `LU -> куст -> скважина` с количеством скважин и суммой `NIZ`;
- клик по `ГТМ` показывает выбранную версию GTM dataset, компактную строку загрузки/выбора файла и сводную таблицу `LU -> куст -> скважина` с количеством мероприятий и приростами нефти / жидкости / газа;
- клик по `Характеристике вытеснения` показывает выбор `LU` кнопками, `SLOY`, компактные excel-like таблицы и диаграммы рядом с ними, а также decline rows для `Base` и `New wells`;
- клик по `KRS ограничениям` показывает отдельные вкладки:
  - `Бригады` с количеством бригад по месяцам и `LU`;
  - `Отказность` с коэффициентами по `LU / SLOY`;
  - `Длительности` с длительностями по типам мероприятий;
- клик по `Forecast` показывает только статус расчёта `Module B` и состав привязанных входов; этот узел не должен показывать настройки optimizer, не должен требовать ограничений для запуска, а запуск расчёта должен происходить только верхней кнопкой `Рассчитать`;
- клик по `KRS Optimizer` показывает настройки `Module D`: режим построения графика, целевую функцию, политику infra constraints, heuristic mode и служебные параметры optimizer;
- клик по `Экономике` показывает `Net Back` по `LU`, таблицу стоимостей мероприятий по типам и сводку `EconomicsConfig`;
- клик по `Infrastructure` показывает иерархическую таблицу `ИТОГО -> ПСП -> объект -> дочерний объект -> куст -> скважина` и отдельную диаграмму-срез по жидкости, нефти и газу для выбранного узла.

Все иерархические таблицы в `Module G` должны поддерживать свёртку и развёртку узлов:

- `Wells`
- `NIZ`
- `ГТМ`
- `Infrastructure`
- `Добыча`

Для всех этих таблиц parent-узлы должны иметь явный toggle-контрол, а leaf-узлы должны отображаться только при раскрытии соответствующей ветки.

Для узлов `Wells`, `ГТМ`, `Infrastructure` `Scenario workbench` не должен содержать отдельных панелей `Реестр datasets` и `Детали dataset`.

Вместо этого должна использоваться одна компактная строка загрузки и выбора:

- сохранённый файл;
- лист Excel;
- имя dataset;
- активная версия dataset;
- кнопки:
  - `Загрузить Excel`
  - `Открыть`
  - `Сопоставление`
  - `Сохранить dataset`

`Mapping колонок` не должен постоянно занимать место в нижнем workbench. Он должен открываться как всплывающее окно после загрузки Excel или по кнопке `Сопоставление`.

Во всплывающем окне должны отображаться:

- список найденных колонок Excel;
- список целевых полей для выбранного `source_kind`;
- автоматические предложения сопоставления;
- выделение обязательных полей;
- возможность одним действием согласиться с предложенным mapping, если он корректен.

## Раздел `Добыча`

### Назначение

Раздел отвечает за просмотр рассчитанных сценариев добычи и заерархический анализ профиля без редактирования самой расчётной логики.

### Основные элементы

- компактный dropdown выбора сценария расчёта
- кнопки-срезы выбора вида добычи:
  - `Нефть`
  - `Жидкость`
  - `Газ`
- переключатель режима отображения:
  - `День`
  - `Месяц`
  - `Год`
- диаграмма добычи нефти по периоду расчёта в выбранном режиме детализации
- накопленная добыча нефти линией поверх периодических значений
- категории диаграммы:
  - `БАЗА`
  - `ГТМ`
  - `ВНС`
- таблица полной иерархии:
  - `Итого`
  - `LU`
  - `SLOY`
  - `WellPad`
  - `скважина`

### Поведение

- пользователь может выбрать один или несколько узлов иерархии кликом по строкам
- при выборе одного узла диаграмма обновляется только по этому элементу и его leaf-скважинам
- при добавлении дополнительных узлов диаграмма должна показывать сумму по всем выбранным leaf-скважинам без двойного учета пересекающихся веток
- если ничего не выбрано, диаграмма показывает весь сценарий
- для сценария должен отображаться период расчёта и сводные показатели по выбранной группе
- кнопки `Нефть / Жидкость / Газ` должны менять и график, и нижнюю иерархическую таблицу, не меняя сами saved outputs `Module B`
- кнопки `День`, `Месяц`, `Год` должны менять только способ агрегирования уже сохранённых outputs `Module B`
- в режиме `День` отображается посуточная добыча
- в режиме `Месяц` отображается добыча, агрегированная по календарным месяцам
- в режиме `Год` отображается добыча, агрегированная по календарным годам
- категории `БАЗА`, `ГТМ`, `ВНС` должны отображаться как периодические значения по выбранному шагу агрегирования
- накопленная добыча должна отображаться отдельной линией поверх тех же периодических значений
- слой `БАЗА` должен строиться по связанному производному сценарию `чистая База`
- слой `ГТМ` должен строиться как разница между активным сценарием и связанным сценарием `чистая База` по фонду, отличному от `New wells`
- слой `ВНС` должен строиться по `New wells` активного сценария
- график должен иметь оси, подписи осей и отображение значений при наведении
- для оси дат в режиме `День` должны использоваться компактные недельные отметки, начиная с первого дня каждого месяца
- для режимов `Месяц` и `Год` ось дат должна оставаться компактной и соответствовать выбранному шагу агрегирования
- нижняя иерархическая таблица должна быть расширена вправо временным рядом:
  - колонки дат по выбранному шагу агрегации;
  - ячейки значений по выбранной метрике `Нефть / Жидкость / Газ`;
  - горизонтальный scroll допускается и считается нормальным поведением для дневного режима

### Контрактные требования

- раздел работает поверх scenario outputs из `Module B`
- dropdown выбора сценария должен быть компактным и пригодным для постоянного размещения в toolbar
- переключатель `День / Месяц / Год` должен быть компактным и пригодным для постоянного размещения в toolbar раздела `Добыча`
- переключатель `Нефть / Жидкость / Газ` должен быть компактным и пригодным для постоянного размещения в toolbar раздела `Добыча`
- `WellForecastResult` должен содержать достаточно полей для иерархической агрегации:
  - `lu_id`
  - `sloy_id`
  - `well_pad_id`
  - `well_id`
  - `fund_type`
- `ProductionPoint` внутри `WellForecastResult` должен содержать посуточные `oil_rate`, `liquid_rate`, `gas_rate`, достаточные для повторной UI-агрегации в дневные и месячные buckets без пересчёта forecast math
- UI раздела `Добыча` не должен пересчитывать forecast math, а только агрегировать и фильтровать уже сохранённые scenario outputs
- UI раздела `Добыча` не должен пересчитывать `Module B`, а только переагрегировать сохранённые посуточные точки в дневные, месячные или годовые buckets
- UI раздела `Добыча` может сравнивать и агрегировать несколько уже сохранённых scenario outputs, если один из них является связанным сценарием `чистая База`
- dropdown выбора сценария должен оставаться компактным и пригодным для постоянного размещения в toolbar вместе с переключателем `День / Месяц / Год`
- автоматически сформированный служебный сценарий `чистая База` не должен подменять основной пользовательский выбор сценария в главном dropdown и в основном списке сценариев; он используется UI внутренне как источник слоя `БАЗА`

## Лист 1. Загрузка

### Назначение

Лист отвечает за выбор и загрузку исходных наборов данных, которыми владеет `Module A`.

Лист расположен в нижнем `Scenario workbench` и не является самостоятельным top-level разделом sidebar.

### Роль в сценарии

На листе пользователь:

- создаёт новый сценарий или выбирает существующий сценарий из списка;
- выбирает источник графика КРС;
- загружает или выбирает datasets, которые будут принадлежать текущему сценарию;
- видит статус полноты сценария по обязательным входам.

### Обязательные входы сценария

Для сценария должны быть доступны ссылки на входные сущности из `core-data-model`:

- `wells` через `DatasetReference`;
- `gtm` через `DatasetReference`;
- `infrastructure` через `DatasetReference`, если сценарий требует infra-check;
- `external_krs_schedule` через `DatasetReference`, если пользователь выбрал загрузку существующего графика КРС;
- `ManualInputReference`.

### Состояния сценария на листе

Лист должен явно показывать для текущего сценария:

- создан ли сценарий;
- выбран ли источник графика КРС;
- привязан ли `wells`;
- привязан ли `gtm`;
- привязан ли `infrastructure`;
- привязан ли `ManualInputSet`;
- готов ли сценарий к расчёту.

### Кнопки

1. `Загрузить существующий график КРС`
2. `Загрузить базовый фонд`
3. `Загрузить план ГТМ`
4. `Загрузить ограничения инфраструктуры`

### Поведение кнопок

#### 1. Загрузить существующий график КРС

Назначение:

- загрузить внешний готовый график КРС;
- нормализовать его через `Module A`;
- сохранить как dataset типа `external_krs_schedule`;
- открыть его в `Module F: Planner`.

Дополнительное правило:

- при открытии такого графика в planner создаётся новая planner-версия с типом `загруженный`.
- при выборе режима `Загрузить существующий график КРС` создаётся или выбирается текущий активный сценарий;
- импортированный `external_krs_schedule` привязывается к этому сценарию как источник графика КРС;
- остальные обязательные входы сценария должны быть выбраны отдельно, если они ещё не привязаны.

#### 2. Загрузить базовый фонд

Назначение:

- загрузить `WellState`;
- сохранить нормализованный dataset типа `wells`;
- использовать его как базовый фонд для расчёта сценария.

#### 3. Загрузить план ГТМ

Назначение:

- загрузить `GtmCandidate`;
- сохранить нормализованный dataset типа `gtm`;
- использовать его как вход для расчёта и оптимизации.

#### 4. Загрузить ограничения инфраструктуры

Назначение:

- загрузить `InfrastructureObject` и связанные инфраструктурные связи;
- сохранить нормализованный dataset типа `infrastructure`;
- использовать его как вход для `Module E`.

### Дополнительные элементы листа

На листе должны быть:

- реестр уже загруженных datasets;
- статус загрузки по каждому типу источника;
- рабочая область preview и normalizing/mapping для текущего файла;
- имя активного dataset;
- версия dataset;
- краткий validation summary;
- действие `Открыть в Planner` для `external_krs_schedule`.

## Лист 2. Характеристики пласта

### Назначение

Лист отвечает за ручной ввод и редактирование параметров пласта и вытеснения.

### Основные блоки

- `DisplacementConfig`
- зависимость обводнённости от отбора от НИЗ
- выбор области действия характеристики:
  - `LU`
  - `SLOY`, если характеристика задаётся на уровне слоя
- предзаполненная таблица обводнённости с шагом `5%`
- ввод значений `NIZ` по строкам таблицы с поддержкой вставки столбца через `Ctrl+V`
- параметры падения жидкости во времени, разделённые на:
  - `Base`
  - `New wells`
- дополнительные параметры пласта, если будут расширяться позже

### Требования

- данные сохраняются как `ManualInputSet`;
- значения должны быть доступны `Module B`;
- для характеристики вытеснения пользователь должен иметь возможность выбирать `LU` и при необходимости уточнять `SLOY`;
- таблица характеристики вытеснения должна быть предзаполнена строками по обводнённости с шагом `5%`;
- колонка `NIZ` должна поддерживать массовую вставку значений через `Ctrl+V`;
- блок снижения жидкости должен быть разделён на два независимых ряда:
  - для `Base`
  - для `New wells`;
- оба ряда снижения жидкости должны быть предзаполнены на `24` месяца;
- для `Base` значение по умолчанию — `5%` в год на весь период;
- для `New wells` значения по умолчанию:
  - `50%` на первый год
  - `5%` далее;
- лист не должен содержать расчётной логики, только ввод и сохранение.

## Лист 4. Ограничения бригад

### Назначение

Лист отвечает за ввод ресурсных ограничений КРС, используемых `Module D` при построении и оптимизации графика.

### Основные блоки

- `BrigadeCapacityByLuConfig` — количество бригад КРС по месяцам и участкам недр (`LU`) начиная с текущего месяца
- `FailureCoefficientConfig` — коэффициент отказности по участкам недр (`LU`) или по слоям (`SLOY`)
- `KrsResourceConfig` — длительности мероприятий по типам работ и общие ресурсные правила

### Требования

- данные сохраняются не в один объект, а в набор конфигураций внутри `ManualInputSet`:
  - `BrigadeCapacityByLuConfig`
  - `FailureCoefficientConfig`
  - `KrsResourceConfig`
- значения должны использоваться `Module D`;
- лист должен быть отделён от самого planner и от drag-and-drop логики.
- лист должен поддерживать помесячный ввод количества бригад по `LU`;
- лист должен позволять задавать коэффициент отказности отдельно по `LU` и отдельно по `SLOY`.

## Лист 5. Схема работы оптимизатора

### Назначение

Лист отвечает за настройку того, как `Module D` строит и оптимизирует график.

### Основные блоки

- режим построения графика
- целевая функция
- горизонт расчёта сценария
- правила отбора сценариев
- режим реакции на инфраструктурные ограничения
- параметры перебора / эвристики
- стратегия работы с planner revisions

### Требования

- лист управляет конфигурацией запуска `Module D`, но не реализует оптимизатор внутри UI;
- все настройки должны передаваться как backend payload;
- при создании нового расчётного сценария поле горизонта должно быть заполнено значением по умолчанию: от даты запуска сценария до `31 декабря` следующего календарного года;
- если пользователь не меняет горизонт вручную, UI должен передавать этот default horizon в расчётный контур как явное значение сценария;
- лист должен позволять запуск:
  - только построения графика;
  - построения + оптимизации.

## Входы

- datasets из `Module A`
- production outputs из `Module B`
- economics outputs из `Module C`
- optimization outputs из `Module D`
- planner revisions из `Module F`

## Список сценариев

`Module G` должен содержать отдельный список сценариев.

Для каждого сценария отображаются:

- `scenario_id`
- `name`
- `source_type`
- `parent_scenario_id`
- временное окно
- привязанные datasets
- привязанный `ManualInputSet`
- статус расчёта
- наличие planner-side версии
- происхождение сценария:
  - создан пользователем
  - создан на основе внешнего графика КРС
  - создан на основе planner revision

Список сценариев является главным входом в сценарный workflow.

## Выходы

- пользовательские сценарии
- orchestration state
- команды на запуск расчёта
- команды на запуск оптимизации
- команды на открытие графика в planner
- команды на повторный расчёт после planner revision

## Зона ответственности

- сценарный интерфейс подготовки входных данных
- интерфейс ручных вводных
- интерфейс запуска расчёта
- интерфейс запуска оптимизации
- интерфейс просмотра рассчитанной добычи и иерархической агрегации scenario outputs
- импорт revision из planner
- запуск recalculation по planner revision
- сравнение сценариев
- сценарный UI от загрузки до feedback loop

## Не входит

- raw Excel import logic
- forecast math
- economics math
- optimizer logic
- drag-and-drop логика planner
- владение editable schedule

## Зависимости

- использует `Module A` как источник datasets и manual inputs
- использует outputs `Module B`, `Module C`, `Module D`
- получает revisions из `Module F`
- инициирует обратный пересчёт в `Module B` и `Module C`
- не является source of truth для самого `PlannerScheduleRevision`, а использует revision, принадлежащий `Module F`

## Возврат из Planner

Если график возвращается из `Module F: Planner` через действие `Создать версию`, новая версия должна автоматически появляться в списке сценариев `Module G`.

Для `Module G` это означает:

- UI не должен требовать повторного ручного создания сценария;
- UI должен автоматически формировать новый элемент списка сценариев на основе активного сценария и нового `PlannerScheduleRevision`;
- новый сценарий должен быть визуально помечен как производный и иметь связь с родительским сценарием;
- новый planner-derived сценарий должен автоматически становиться текущим active scenario для `Сценарии`, `Добыча` и `Planner`;
- `Module G` остаётся владельцем сценарного списка и автоматического создания новой версии сценария на основе revision.

## Контрактные правила

1. `Module G` не владеет editable schedule planner.
2. `Module G` не дублирует backend business logic.
3. Любой recalculation после planner edit создаёт новый сценарий, а не переписывает старый.
4. Лист `Загрузка` работает поверх datasets и references, а не поверх временного file-state.
5. Внешний график КРС открывается в planner через устойчивый runtime flow по `dataset_reference`.
6. Тип planner-версии, созданной из внешнего графика КРС, должен быть `загруженный`.
7. Листы ручного ввода не должны хранить единственный источник истины в локальном UI-state; все рабочие значения должны быть сохраняемыми в `ManualInputSet`.
8. Действие `Создать версию` в `Planner` должно приводить к автоматическому появлению новой версии сценария в списке `Module G` без ручного шага создания сценария пользователем.
