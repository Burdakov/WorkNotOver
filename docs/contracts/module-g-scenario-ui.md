# Контракт Module G

## Модуль

`Module G: Сценарный UI и обратный пересчёт`

## Назначение

`Module G` владеет пользовательским сценарным контуром работы с системой и оркестрирует:

- загрузку и выбор исходных данных;
- ввод ручных параметров;
- запуск расчёта;
- запуск оптимизации;
- открытие графика в `Planner`;
- повторный пересчёт после `planner revisions`.

`Module G` не владеет самим editable-графиком `Planner`, но владеет пользовательским сценарием движения по системе от загрузки входных данных до получения нового сценария.
При этом при planner-side recalculation сам `PlannerScheduleRevision` читается `Module B` напрямую из `Module F`, а `Module G` оркестрирует запуск и пользовательский поток пересчёта.

## Принцип Scenario-first

`Module G` строится вокруг сущности `Scenario`, а не вокруг набора независимых листов ввода.

Любой пользовательский workflow в `Module G` начинается с выбора существующего сценария или создания нового.

Каждый сценарий должен иметь собственные ссылки на входные данные и собственные сценарные атрибуты, определённые в `core-data-model`, включая:

- `DatasetReference` для обязательных dataset-входов;
- `ManualInputReference`;
- `source_type`;
- `parent_scenario_id`, если сценарий производный;
- временное окно сценария;
- связанные outputs расчёта и planner-side revisions.

`Module G` не определяет состав сценарных атрибутов заново, а использует канонические сущности из `core-data-model`.

## Дерево workflow сценария

Интерфейс `Module G` должен визуализировать сценарный workflow как дерево состояний.

Базовый workflow:

1. `Создать новый сценарий`
2. `Выбрать источник графика КРС`
3. `Собрать входные данные сценария`
4. `Проверить полноту сценария`
5. `Запустить расчёт`
6. `Открыть / передать в Planner`
7. `Получить planner revision`
8. `Создать новую версию сценария`

### Узел 1. Создать новый сценарий

Пользователь создаёт новый `Scenario` или выбирает существующий сценарий из списка.

На этом шаге задаются базовые атрибуты сценария:

- `name`
- `source_type`
- `parent_scenario_id`, если сценарий производный
- `forecast_start_date`
- `forecast_end_date`

### Узел 2. Выбрать источник графика КРС

Пользователь выбирает один из двух вариантов:

- `Новый график КРС`
- `Загрузить существующий график КРС`

Если выбран `Новый график КРС`, дальнейшее формирование графика идёт через расчётно-оптимизационный контур.

Если выбран `Загрузить существующий график КРС`, используется dataset типа `external_krs_schedule`, загруженный через `Module A`.

Выбор источника графика КРС не заменяет создание сценария, а является частью атрибутов сценарного workflow.

## Основная UI-структура

В левом sidebar должны существовать три разных раздела верхнего уровня:

- `Исходные данные`
- `Добыча`
- `Планировщик КРС`

`Исходные данные` — это новый сценарный раздел `Module G`, который заменяет текущий старый раздел `Загрузка графика`.

`Добыча` — это отдельный сценарный раздел `Module G`, который отображает сохранённые результаты `Module B`, даёт выбрать сценарий расчёта и анализировать профиль добычи по иерархии `LU -> SLOY -> WellPad -> скважина`. 

`Планировщик КРС` — это отдельный готовый модуль `Module F: Planner`, а не один из листов сценарного UI.

В `Module G` вводится единый сценарный экран с листами:

1. `Загрузка`
2. `Характеристики пласта`
3. `Экономические вводные`
4. `Ограничения бригад`
5. `Схема работы оптимизатора`

Эти листы образуют основной UI-контур подготовки сценария.

## Раздел `Добыча`

### Назначение

Раздел отвечает за просмотр рассчитанных сценариев добычи и заерархический анализ профиля без редактирования самой расчётной логики.

### Основные элементы

- компактный dropdown выбора сценария расчёта
- накопительная диаграмма добычи нефти по периоду расчёта
- категории диаграммы:
  - `БАЗА`
  - `ГТМ`
  - `ВНС`
- таблица полной иерархии:
  - `Итого`
  - `LU`
  - `SLOY`
  - `WellPad`
  - `скважина`

### Поведение

- пользователь может выбрать один или несколько узлов иерархии кликом по строкам
- при выборе узлов диаграмма обновляется только по выбранной группе скважин
- если ничего не выбрано, диаграмма показывает весь сценарий
- для сценария должен отображаться период расчёта и сводные показатели по выбранной группе
- категории `БАЗА`, `ГТМ`, `ВНС` должны отображаться накопительно на период расчёта

### Контрактные требования

- раздел работает поверх scenario outputs из `Module B`
- dropdown выбора сценария должен быть компактным и пригодным для постоянного размещения в toolbar
- `WellForecastResult` должен содержать достаточно полей для иерархической агрегации:
  - `lu_id`
  - `sloy_id`
  - `well_pad_id`
  - `well_id`
  - `fund_type`
- UI раздела `Добыча` не должен пересчитывать forecast math, а только агрегировать и фильтровать уже сохранённые scenario outputs

## Лист 1. Загрузка

### Назначение

Лист отвечает за выбор и загрузку исходных наборов данных, которыми владеет `Module A`.

### Роль в сценарии

На листе пользователь:

- создаёт новый сценарий или выбирает существующий сценарий из списка;
- выбирает источник графика КРС;
- загружает или выбирает datasets, которые будут принадлежать текущему сценарию;
- видит статус полноты сценария по обязательным входам.

### Обязательные входы сценария

Для сценария должны быть доступны ссылки на входные сущности из `core-data-model`:

- `wells` через `DatasetReference`;
- `gtm` через `DatasetReference`;
- `infrastructure` через `DatasetReference`, если сценарий требует infra-check;
- `external_krs_schedule` через `DatasetReference`, если пользователь выбрал загрузку существующего графика КРС;
- `ManualInputReference`.

### Состояния сценария на листе

Лист должен явно показывать для текущего сценария:

- создан ли сценарий;
- выбран ли источник графика КРС;
- привязан ли `wells`;
- привязан ли `gtm`;
- привязан ли `infrastructure`;
- привязан ли `ManualInputSet`;
- готов ли сценарий к расчёту.

### Кнопки

1. `Загрузить существующий график КРС`
2. `Загрузить базовый фонд`
3. `Загрузить план ГТМ`
4. `Загрузить ограничения инфраструктуры`

### Поведение кнопок

#### 1. Загрузить существующий график КРС

Назначение:

- загрузить внешний готовый график КРС;
- нормализовать его через `Module A`;
- сохранить как dataset типа `external_krs_schedule`;
- открыть его в `Module F: Planner`.

Дополнительное правило:

- при открытии такого графика в planner создаётся новая planner-версия с типом `загруженный`.
- при выборе режима `Загрузить существующий график КРС` создаётся или выбирается текущий активный сценарий;
- импортированный `external_krs_schedule` привязывается к этому сценарию как источник графика КРС;
- остальные обязательные входы сценария должны быть выбраны отдельно, если они ещё не привязаны.

#### 2. Загрузить базовый фонд

Назначение:

- загрузить `WellState`;
- сохранить нормализованный dataset типа `wells`;
- использовать его как базовый фонд для расчёта сценария.

#### 3. Загрузить план ГТМ

Назначение:

- загрузить `GtmCandidate`;
- сохранить нормализованный dataset типа `gtm`;
- использовать его как вход для расчёта и оптимизации.

#### 4. Загрузить ограничения инфраструктуры

Назначение:

- загрузить `InfrastructureObject` и связанные инфраструктурные связи;
- сохранить нормализованный dataset типа `infrastructure`;
- использовать его как вход для `Module E`.

### Дополнительные элементы листа

На листе должны быть:

- реестр уже загруженных datasets;
- статус загрузки по каждому типу источника;
- имя активного dataset;
- версия dataset;
- краткий validation summary;
- действие `Открыть в Planner` для `external_krs_schedule`.

## Лист 2. Характеристики пласта

### Назначение

Лист отвечает за ручной ввод и редактирование параметров пласта и вытеснения.

### Основные блоки

- `DisplacementConfig`
- зависимость обводнённости от отбора от НИЗ
- выбор области действия характеристики:
  - `LU`
  - `SLOY`, если характеристика задаётся на уровне слоя
- предзаполненная таблица обводнённости с шагом `5%`
- ввод значений `NIZ` по строкам таблицы с поддержкой вставки столбца через `Ctrl+V`
- параметры падения жидкости во времени, разделённые на:
  - `Base`
  - `New wells`
- дополнительные параметры пласта, если будут расширяться позже

### Требования

- данные сохраняются как `ManualInputSet`;
- значения должны быть доступны `Module B`;
- для характеристики вытеснения пользователь должен иметь возможность выбирать `LU` и при необходимости уточнять `SLOY`;
- таблица характеристики вытеснения должна быть предзаполнена строками по обводнённости с шагом `5%`;
- колонка `NIZ` должна поддерживать массовую вставку значений через `Ctrl+V`;
- блок снижения жидкости должен быть разделён на два независимых ряда:
  - для `Base`
  - для `New wells`;
- оба ряда снижения жидкости должны быть предзаполнены на `24` месяца;
- для `Base` значение по умолчанию — `5%` в год на весь период;
- для `New wells` значения по умолчанию:
  - `50%` на первый год
  - `5%` далее;
- лист не должен содержать расчётной логики, только ввод и сохранение.

## Лист 3. Экономические вводные

### Назначение

Лист отвечает за ручной ввод экономических параметров сценария.

### Основные блоки

- Учаток недр (LU)
- Net Back

### Требования

- данные сохраняются как `ManualInputSet`;
- значения должны быть доступны `Module C`;
- UI должен поддерживать отдельные версии экономических вводных.

---

## Лист 4. Ограничения бригад

### Назначение

Лист отвечает за ввод ресурсных ограничений КРС, используемых `Module D` при построении и оптимизации графика.

### Основные блоки

- `BrigadeCapacityByLuConfig` — количество бригад КРС по месяцам и участкам недр (`LU`) начиная с текущего месяца
- `FailureCoefficientConfig` — коэффициент отказности по участкам недр (`LU`) или по слоям (`SLOY`)
- `KrsResourceConfig` — длительности мероприятий по типам работ и общие ресурсные правила

### Требования

- данные сохраняются не в один объект, а в набор конфигураций внутри `ManualInputSet`:
  - `BrigadeCapacityByLuConfig`
  - `FailureCoefficientConfig`
  - `KrsResourceConfig`
- значения должны использоваться `Module D`;
- лист должен быть отделён от самого planner и от drag-and-drop логики.
- лист должен поддерживать помесячный ввод количества бригад по `LU`;
- лист должен позволять задавать коэффициент отказности отдельно по `LU` и отдельно по `SLOY`.

---

## Лист 5. Схема работы оптимизатора

### Назначение

Лист отвечает за настройку того, как `Module D` строит и оптимизирует график.

### Основные блоки

- режим построения графика
- целевая функция
- горизонт расчёта сценария
- правила отбора сценариев
- режим реакции на инфраструктурные ограничения
- параметры перебора / эвристики
- стратегия работы с planner revisions

### Требования

- лист управляет конфигурацией запуска `Module D`, но не реализует оптимизатор внутри UI;
- все настройки должны передаваться как backend payload;
- при создании нового расчётного сценария поле горизонта должно быть заполнено значением по умолчанию: от даты запуска сценария до `31 декабря` следующего календарного года;
- если пользователь не меняет горизонт вручную, UI должен передавать этот default horizon в расчётный контур как явное значение сценария;
- лист должен позволять запуск:
  - только построения графика;
  - построения + оптимизации.

## Входы

- datasets из `Module A`
- production outputs из `Module B`
- economics outputs из `Module C`
- optimization outputs из `Module D`
- planner revisions из `Module F`

## Список сценариев

`Module G` должен содержать отдельный список сценариев.

Для каждого сценария отображаются:

- `scenario_id`
- `name`
- `source_type`
- `parent_scenario_id`
- временное окно
- привязанные datasets
- привязанный `ManualInputSet`
- статус расчёта
- наличие planner-side версии
- происхождение сценария:
  - создан пользователем
  - создан на основе внешнего графика КРС
  - создан на основе planner revision

Список сценариев является главным входом в сценарный workflow.

## Выходы

- пользовательские сценарии
- orchestration state
- команды на запуск расчёта
- команды на запуск оптимизации
- команды на открытие графика в planner
- команды на повторный расчёт после planner revision

## Зона ответственности

- сценарный интерфейс подготовки входных данных
- интерфейс ручных вводных
- интерфейс запуска расчёта
- интерфейс запуска оптимизации
- интерфейс просмотра рассчитанной добычи и иерархической агрегации scenario outputs
- импорт revision из planner
- запуск recalculation по planner revision
- сравнение сценариев
- сценарный UI от загрузки до feedback loop

## Не входит

- raw Excel import logic
- forecast math
- economics math
- optimizer logic
- drag-and-drop логика planner
- владение editable schedule

## Зависимости

- использует `Module A` как источник datasets и manual inputs
- использует outputs `Module B`, `Module C`, `Module D`
- получает revisions из `Module F`
- инициирует обратный пересчёт в `Module B` и `Module C`
- не является source of truth для самого `PlannerScheduleRevision`, а использует revision, принадлежащий `Module F`

## Возврат из Planner

Если график возвращается из `Module F: Planner` через действие `Создать версию`, новая версия должна автоматически появляться в списке сценариев `Module G`.

Для `Module G` это означает:

- UI не должен требовать повторного ручного создания сценария;
- UI должен автоматически формировать новый элемент списка сценариев на основе активного сценария и нового `PlannerScheduleRevision`;
- новый сценарий должен быть визуально помечен как производный и иметь связь с родительским сценарием;
- `Module G` остаётся владельцем сценарного списка и автоматического создания новой версии сценария на основе revision.

## Контрактные правила

1. `Module G` не владеет editable schedule planner.
2. `Module G` не дублирует backend business logic.
3. Любой recalculation после planner edit создаёт новый сценарий, а не переписывает старый.
4. Лист `Загрузка` работает поверх datasets и references, а не поверх временного file-state.
5. Внешний график КРС открывается в planner через устойчивый runtime flow по `dataset_reference`.
6. Тип planner-версии, созданной из внешнего графика КРС, должен быть `загруженный`.
7. Листы ручного ввода не должны хранить единственный источник истины в локальном UI-state; все рабочие значения должны быть сохраняемыми в `ManualInputSet`.
8. Действие `Создать версию` в `Planner` должно приводить к автоматическому появлению новой версии сценария в списке `Module G` без ручного шага создания сценария пользователем.
